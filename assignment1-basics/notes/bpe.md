# BPE 学习笔记

BPE 是一种从语料中学习如何将文本切分为 token 的分词方法。它以 256 个字节作为初始词表，通过反复统计所有预分词单元中相邻对的出现频次，选出全局最高频的一对，将其合并为新 token，并在各单元内部替换原相邻对，同时把新 token 加入词表。新 token 在下一轮中也会与邻居组成新的相邻对参与统计。如此重复，直到词表达到预设大小；若频次相同，则优先选择字典序更大的相邻对。最终产出词表 vocab 和按发生顺序排列的合并记录 merges。

与词级和字节级分词相比，词级分词以一个单词为基本单位，词表庞大、序列短，但无法表示未出现在语料中的词；字节级分词以一个字节为基本单位，词表小（仅 256 个元素），但序列冗长、关系被拉长，更难建立长距离依赖。BPE 得到的词表大小可人为设置，因此可以按需在词表大小和序列长度之间取舍，并很好地折中了两者的不足。

## 代码流程

在 `pretokenization.py` 中，核心函数是 `train_bpe`。它以语料文件路径 `input_path`、预设词表大小 `vocab_size` 和特殊 token 列表 `special_tokens` 为输入，输出训练得到的词表 `vocab` 和按发生顺序排列的合并记录 `merges`。

在 `train_bpe` 中，首先按 `input_path` 读取整个语料文件，得到一段完整文本；然后以特殊 token 为分隔符，将其切分为若干文本段。特殊 token 本身被丢弃，不再参与后续统计。每个文本段按 PAT 正则切分为若干 word，再把每个 word 整体编码为 UTF-8 字节串，并拆成由长度 1 的 `bytes` 对象组成的元组。之所以从字节粒度起步，是因为初始词表只有 256 个字节，而合并只能在词表元素之间进行。随后把这些元组统计进字典 `word_counts`，其中键是 word 拆分后的字节元组，值是该 word 在整个语料中出现的次数。

接着初始化词表，为 0–255 的全部字节值各分配一个 ID，再为每个特殊 token 分配一个固定 ID，因此初始词表大小为 `256 + len(special_tokens)`。特殊 token 之所以必须在训练开始前加入，一方面是因为它的 ID 不会随后续合并次数变化，另一方面是因为编码时它才能被整体映射为单个 token，而不会被拆成多个字节。

随后统计相邻对，遍历 `word_counts` 中每个字节元组的相邻位置，以相邻的两个字节对象作为键，把该 word 在语料中的出现次数累加到 `pairs_counts` 中，而不是每出现一次就加 1。这个字典的键是相邻对，值是该相邻对在整个语料中的加权出现次数。

随后从 `pairs_counts` 中选出本轮要合并的一对，规则是取频次最高者，若频次并列则取字典序更大的那一对。这个选择必须是确定的，否则同一份语料跑两次会得到不同的 `merges`，既无法复现实验，也无法与参考实现逐项比对，已训练好的模型和 tokenizer 之间也会失去对应关系。

选出之后，这一对会被追加进 `merges`，记录的是被合并的两个 token 组成的二元组，而不是拼接后的字节串。同时把两者拼接成的新字节串作为新 token 写入 `vocab`，其 ID 取当前词表长度，因此不会与已有 ID 冲突。随后更新 `word_counts`。由于字典的键不可修改，程序把受影响的旧键删掉、写入新键。对每个受影响的键从头扫描，命中该对就合并并前进两格，否则保留当前元素前进一格，末尾元素无论如何都要保留。若两个不同的旧键合并后撞成同一个新键，频次相加。合并前后所有频次之和应当保持不变。

整个过程循环执行，直到词表长度达到 `vocab_size`。这里直接检查 `len(vocab)` 而不另外维护计数器，因为目标本身就是用词表大小表达的，而合并次数本来就能从词表长度推出来。循环内还有一个兜底出口，当所有预分词都已被合并到只剩单个 token 时，相邻对集合为空，此时没有可合并的对象，应当提前终止。若不加这个判断，`max` 会在空集合上报错。最终函数返回 `vocab` 和 `merges`，前者是 token 到 ID 的映射，后者是按发生顺序排列的合并记录，两者共同构成训练好的分词器。

## 性能优化

第一版是"每轮全量重算"。每轮遍历全部 word 重建 `word_counts`，再遍历全部 word 重建 `pairs_counts`，复杂度是轮数乘以词数。在 `corpus.en` 上训练到 `vocab_size=500`（243 轮），耗时约 1.93 秒，超过测试规定的 1.5 秒上限。

用 cProfile 定位后，耗时集中在两个函数，`apply_merge` 约占 68%，`count_pairs` 约占 27%，而预分词只占 1.3%。这说明瓶颈不在读文件或正则，而在合并循环内部。

进一步的诊断给出了优化的上限。统计发现 `word_counts` 约有 4763 个键，而每轮真正含有被合并那一对的只有 163 到 561 个，占比 3.4% 到 11.8%。也就是说九成以上的遍历是重复劳动。

优化分三处。

第一处是建立 pair 索引，键是相邻对，值是含有该对的 word 集合。它只在训练开始时构建一次，之后每轮增量维护。有了它，就能在常数时间里拿到本轮需要处理的 word，不必再扫描全部词。

第二处是让合并只处理受影响的 word，并改为原地修改 `word_counts`，删掉旧键、写入新键，而不是整体重建。这样每轮的成本只与受影响的 word 数成正比。

第三处是把 `pairs_counts` 从"每轮重建"变成"跨轮维护的状态"。对每个受影响的 word，用 `Counter` 分别统计它的旧序列和新序列里每一对出现几次，再按次数乘以频次算出净变化量更新计数，计数减到 0 就从字典中删除。这一步必须用次数而不能用集合，因为同一对在一个 word 里可能出现多次。

索引的维护有一个容易漏的点。一个 word 被改写后，它的键已经不是原来那个了，所以旧序列里的每一对都要把旧 word 摘掉，新序列里的每一对都要把新 word 加上，即使某一对在两个序列里都出现过，也必须换人。

最终三个测试全部通过，`test_train_bpe_speed` 的耗时已降到 1.5 秒以内（实测约 ______ 秒）。

整个优化过程中反复使用的三条不变量。

`sum(word_counts.values())` 在每轮前后保持不变，用于检查频次是否丢失或重复。

`pairs_counts` 中任何一对的计数都不应出现负数，负数说明某个 word 的旧贡献被减了两次。

被合并的那一对在下一轮必须从 `pairs_counts` 中消失，否则说明计数没有正确撤销。
